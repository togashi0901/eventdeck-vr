# EventDeck VR 抽選仕様書 (algorithm_version: v1)

対応文書: 「EventDeckVR_要件定義書」「01_DB設計書_EventDeckVR.md」
リファレンス実装: `lottery_v1.py`(検証テスト `test_lottery_v1.py`、11件パス済み)

**この仕様書とリファレンス実装が抽選ロジックの正である。** 実装時は `lottery_v1.py` の `run_lottery()` をサービス層に組み込み、挙動を変更する場合は `algorithm_version` を上げて旧バージョンの実装を残すこと(過去の抽選の再現性を壊さないため)。

---

## 1. 用語

| 用語 | 意味 |
|---|---|
| 枠(quota) | 当選者を選ぶ区分。優先枠(初参加者枠など)と一般枠がある |
| 一般枠 | `count=null` の枠。優先枠で埋まらなかった残定員をすべて吸収する。常に最後に1つだけ置く |
| 補欠(waitlist) | 当選者のキャンセル時に繰り上げる候補者 |
| 残定員 | `events.capacity` −(その時点の `status='won'` の応募数) |
| round | 同一イベント内での抽選実行回数。通常は1回で完結する |

## 2. 抽選設定(`lotteries.config` のJSON形式)

主催者が抽選実行画面で設定した内容を、実行時にこの形式でスナップショット保存する。

```json
{
  "quotas": [
    { "name": "first_timer", "label": "初参加者優先枠", "count": 10, "filter": "first_timer" },
    { "name": "general",     "label": "一般枠",         "count": null, "filter": "all" }
  ],
  "waitlist_count": 5
}
```

制約(リファレンス実装が `ValueError` で強制するもの):
- `count=null` の枠は**最大1つ**で、必ず**配列の最後**に置く。
- `count` 指定枠の合計は残定員以下でなければならない。
- 優先枠を使わない場合は `quotas` を一般枠1つだけにする(これがデフォルト)。

### filter の定義(v1で提供する3種)

| filter | 合致条件(実行時点で評価) |
|---|---|
| `all` | 常に合致 |
| `first_timer` | 応募者が、**同じ organization の過去イベント**(`starts_at` が対象イベントより前)で `checkins` を1件も持たない |
| `repeater` | `first_timer` の否定(過去に1回以上入場実績がある) |

評価はSQLで行う(概念):

```sql
-- application A が first_timer かどうか
SELECT NOT EXISTS (
  SELECT 1 FROM checkins c
  JOIN events e ON e.id = c.event_id
  JOIN applications a2 ON a2.id = c.application_id
  WHERE a2.user_id = A.user_id
    AND e.organization_id = :対象イベントのorganization_id
    AND e.starts_at < :対象イベントのstarts_at
);
```

`checkins` は追記専用(削除・更新しない)ため、`executed_at` 以前のデータで評価する限り後日の再評価でも同じ結果になる。

## 3. 実行の前提条件(サービス層でチェック)

1. 実行者は対象イベントの organization に所属する主催者であること。
2. イベントの `status` が `published` または `closed` で、`apply_ends_at` を過ぎていること(締切前の抽選は禁止)。
3. `selection_method = 'lottery'` であること(`first_come` のイベントでは抽選を実行できない)。
4. 残定員 > 0 であること。
5. 同一イベントで実行中の抽選トランザクションがないこと(イベント単位のロックを取る)。

## 4. アルゴリズム(v1)

入力: 対象応募ID集合、quotas、残定員、waitlist_count、seed。
seed は実行時に `secrets.randbits(63)` で生成し、`lotteries.seed` に保存する。

1. **正規順序化**: 対象応募IDを文字列昇順にソートする(入力順に結果が依存しないため)。
2. **シャッフル**: `random.Random(seed)` (Mersenne Twister) の `shuffle()` で並べ替える。並び順が `draw_rank`(1始まり)。
3. **枠の適用**: `quotas` を定義順に処理する。各枠について、シャッフル順に走査し、未選出かつ filter に合致する応募を枠の `count` まで(かつ全体で残定員まで)当選にする。一般枠(`count=null`)は残定員をすべて吸収する。
4. **補欠の選出**: 未当選者のうちシャッフル順の先頭から `waitlist_count` 名を `waitlisted` にする。
5. **残りは落選**: 未当選・非補欠の全員を `lost` にする。

### 決定性(公平性の証跡)

以下がテストで検証済み:
- 同じ(応募集合・設定・seed)からは常に同一の結果が得られる。
- 入力リストの順序は結果に影響しない。
- 当選数は必ず指定どおり、draw_rank は 1..N の順列になる。

### エッジケース

| ケース | 挙動 |
|---|---|
| 定員割れ(応募数 ≤ 残定員) | 全員当選。補欠は発生しない(検証済み) |
| 優先枠の合致者が枠数未満 | 合致者全員を当選にし、余った席は後続の枠(通常は一般枠)が吸収する。**総当選数は変わらない**(検証済み) |
| 応募0件 | 抽選を実行せずエラーを返す(サービス層) |
| waitlist_count が未当選者数を超える | 未当選者全員が補欠になる |

## 5. DBへの書き込み(1トランザクション)

```
BEGIN;
  1. lotteries に1行 INSERT (event_id, round, executed_by, seed, algorithm_version='v1',
     winner_quota=実際の当選数, waitlist_quota=実際の補欠数, config=スナップショット)
  2. lottery_results に全対象ぶん INSERT (result, draw_rank, quota_name)
     - won の quota_name = 当選した枠名 / waitlisted = 'waitlist' / lost = 'none'
  3. applications.status を results どおりに UPDATE (pending → won/waitlisted/lost)
  4. notifications に当選者・補欠・落選者への通知行を INSERT (status='queued')
     - type: result_won / result_waitlisted / result_lost
     - channel: in_app は全員、email・push は各ユーザーの登録状況に応じて
COMMIT;
```

`lotteries` と `lottery_results` は**追記専用**。UPDATE・DELETEは行わない(監査証跡)。

## 6. round(複数回抽選)の扱い

- **round 1**: 対象 = `status='pending'` の全応募。実行後、pending は残らない。
- **round 2以降(敗者復活抽選)**: 補欠が尽きたのに残定員がある場合に限り、主催者の明示操作で実行できる。対象 = `status='lost'` の応募。当選者は `won`(`promoted=false`。繰り上げではなく再抽選当選)。
- round は `UNIQUE(event_id, round)` で連番管理する。

## 7. キャンセルと繰り上げ(抽選外の状態遷移)

繰り上げは**抽選ではない**。以下の決定的ルールで行う:

1. `won` の応募が `canceled` になったとき、`status='waitlisted'` の応募のうち**「round昇順 → draw_rank昇順」で最上位**の1名を `won` に繰り上げる(`promoted=true`)。
2. 繰り上げ時は `notifications` に `type='promoted'` を INSERT する(in_app + email + push)。
3. 繰り上げはイベントの `starts_at` まで自動で行う(設定でOFF可能。OFF時は主催者が入場管理画面から手動繰り上げ)。
4. イベントが `finished` になった時点で、残っている `waitlisted` を一括で `lost` に変える(クローズ処理)。

## 8. 再現・監査手順

「抽選が公平だったか」を後から示す手順:

1. `lotteries` から seed / algorithm_version / config を取得する。
2. `lottery_results` から対象応募ID集合を取得する(全対象が明細として残っている)。
3. filter の合致判定を「`executed_at` 以前のデータ」で再評価する(checkins は追記専用なので結果は不変)。
4. 該当バージョンの `run_lottery()` に同じ入力を与えて実行し、保存済みの `lottery_results` と一致することを確認する。

このためにアルゴリズムの実装を変更する場合は必ず `algorithm_version` を新設し、旧実装コードを削除しないこと。

## 9. 実装への組み込み指示(Claude Code向け)

- `lottery_v1.py` は純粋関数のため、そのまま `app/services/lottery/v1.py` 等に配置してよい。
- サービス層の責務: 前提条件チェック(§3)、対象応募の取得、filter評価関数の用意(§2のSQL)、seed生成、`run_lottery()` 呼び出し、トランザクション書き込み(§5)。
- `test_lottery_v1.py` はそのままユニットテストとして採用する。サービス層には別途、トランザクション・前提条件・繰り上げ(§7)の統合テストを書くこと。
